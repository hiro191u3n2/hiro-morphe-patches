# Native Page restore integration audit

Runtime API: `NativeRestoreTracker.install(WebView, featureClass, featureMethod, factoryClass, factoryMethod, providerField, allowCreatePeer)`, `navigationId(WebView)`, `consume(WebView, startedUrl)`, `isCurrent(WebView, token, currentUrl)`.

The app's existing canonical support-library boundary interfaces are used reflectively. No duplicate boundary interfaces are packaged. Feature checks try public `NAVIGATION_LISTENER` and legacy `NAVIGATION_LISTENER_V1` before resolving the provider factory. The listener advertises the provider-side feature `WEB_VIEW_NAVIGATION_LISTENER_V1` and uses an inline UI executor. Installation adds a listener; it never replaces the WebView client or existing navigation listeners.

A native restore proof requires a committed, non-error, cross-document history navigation with the exact previously observed native Page peer. Reloads and same-document navigations cannot mint a proof. `isRestore` is not used. Every cross-document start advances an ID; completion must also match the exact canonical Navigation peer retained from that start. The ID is shared with the coordinator so a callback cannot attach to a previous same-URL legacy start. A token is consumed once and is invalidated by a new cross-document start or current Page deletion. A same-document commit can follow a URL only while retaining the same Page.

Chromium returns new boundary handlers/adapters for callbacks. Handler reference identity is therefore unsuitable. `getOrCreatePeer` supplies the stable peer slot, but the slot can already be owned by AndroidX. The patcher only permits creating lightweight Page/Navigation peers if the original app has no Page or Navigation consumers. Otherwise the callable returns null: an existing peer can be compared without replacement, while an empty slot causes native proof to fall back safely. Original Berry 3.83.74 executable-reference inspection found no Page/Navigation consumers; the two generic Isomorphic peer uses belonged to other APIs.

Chromium's AwPage/AwNavigation wrapper caches themselves use weak values. Retaining only weak peers would lose identity after GC. The runtime therefore retains up to 64 Page handlers and their peers in the provider-owned listener State, removing them on `onPageDeleted` and oldest-entry eviction. The static WebView map holds weak State references, and each State holds only a weak WebView reference; there is no static strong path back to a tab or WebView through these wrappers. The current Navigation handler is held only until matching completion/cancellation or the next start. A separate weak-key Boolean map records installation attempts even when an unsupported State is collected.

Missing APIs, unsupported features, absent safe peer identities, or off-UI callback delivery never synthesize success. They leave the JavaScript completion route available (after an in-flight native path becomes invalid, a subsequent legacy start establishes the fallback generation). Failures log once per installed state/identity category, without new user-visible diagnostics.

Validation: full ECJ compilation, D8 extension build, existing coordinator JVM tests (41 scenarios / 73 assertions), document-start JavaScript tests (19 assertions), native tracker tests (5 scenarios / 40 assertions), and native/coordinator integration tests (13 scenarios / 29 assertions) pass. Tests exercise callback-before-start, callback-after-start, same-URL stale callbacks, duplicate completions, cancellation, reload/error/cache miss rejection, current-URL following, deletion, eviction, weak-cache GC pressure, unsupported factory avoidance, empty/foreign peer behavior, once-only logging, optional API failures, and UI-thread ordering. Android rendering and on-device behavior remain untested.
