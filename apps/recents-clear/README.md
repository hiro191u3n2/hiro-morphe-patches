# 履歴クリア 1.21.0（ユーザー補助版）

ホームのアイコンを押すと「最近使ったアプリ」を開き、「すべて閉じる」を操作するAndroid用アプリ。Shizuku・rootは不要。自動・アイコンの両方で、履歴を開く要求が返った直後に一度、新しい画面を確認する方式を使用する。

## 1.21.0：再起動直後の準備不足と消去の反映待ちを修正

再起動後すぐ画面を開いていると履歴が開いたままになり、ロックしたまま待ってから解除すると成功する、という報告に対応。旧版には、起動準備に消費した時間を消去の5秒期限から差し引いてしまう問題と、ボタン操作の受付だけで終了する問題があった。

- 自動実行前に起動途中のSystemUIが見えていて、履歴画面の根拠がない場合は、履歴を開かず準備を待つ。Novaなど別のホームアプリを除外しない。
- 自動実行の最初のUI操作から最大15秒の消去・反映確認時間を確保する。操作できる時は従来どおり即時実行し、15秒を固定で待つ処理にはしない。アイコン操作は従来の5秒枠を維持する。
- 自動消去のクリック受付後も、新しく取得した標準の画面情報で反映を確認する。操作済みの古いノードを再使用しない。
- 同じ履歴画面と同じボタンが残っていることを時間を空けた複数回の確認で検証できた場合だけ、同じ処理内で再試行する。受け付けられるクリックは最大3回。初期の再試行だけで回数を使い切らないよう、最後の再試行は最初の受付から6.5秒以降に残す。拒否される場合も全体の期限と回数上限を守る。
- 履歴を開く要求は繰り返さない。別画面への移動、ロック、消灯、設定OFFでは追加操作を止める。画面が取得できないだけで成功と判定しない。

表示が履歴画面から離れたことと、実際のタスク削除成功は区別して記録する。空の履歴を確認できた場合を除き、単にHOMEへ戻して成功に見せる処理は追加しない。実機で今回どの分岐が発生したか、Samsung端末での表示時間は未確認。

## 1.20.0：2回目以降も即時確認を途切れさせない

初回と学習済みの2回目以降で異なる経路を調査し、保存されたボタンIDがある場合だけ使う軽量な画面取得に、不完全な結果が返ると消去をキューへ戻す箇所を修正した。1.19では履歴要求直後の即時確認がこの軽量取得に使われるため、標準取得への切替で別の処理を待つ場合があった。

- 軽量取得が空・古いホーム・不完全・例外になった場合は、古い画面情報を解放してから、その場で標準取得へ切り替える。
- 履歴要求後の即時確認1回と、軽量取得からの即時復旧1回に制限する。繰り返し予約や再帰を増やさない。
- 自動実行とアイコン実行の両方で同じ消去処理を使う。ボタンがまだ操作できない場合は従来の再確認へ戻す。
- 再起動の検出時期、初回ロック解除待ち、Activityの受け渡しと復旧、起動ごとの重複防止、ロック・消灯・設定OFFの確認を維持する。

「初回に成功して保存された情報を次の再起動へ引き継ぐ」条件と、履歴表示直後に別の処理が入る条件を模擬環境で比較する。実機で今回どの分岐が発生したかは診断未取得のため断定しない。Android側の履歴画面表示や描画を省略する変更ではなく、実機の表示時間は未検証。

## 1.19.0：履歴表示後のアプリ側の待ちを減らす

「履歴画面を開いて閉じるまでを瞬時に」という依頼を受け、自動消去にもアイコン実行の即時確認方式を適用した。1.11／1.12方式の通常予約を維持する方針から変更した。

- 保存したボタン識別情報の最初の読み込みを、履歴画面を開く前に済ませる。ホストやボタンは実際の新しい画面で検証する。
- 履歴を開くAPIが成功して返った直後、古い画面情報を解放してから、同じ呼び出しの中で一度だけ新しい画面を確認する。ボタンが操作可能なら次の予約を挟まずクリックする。
- 消去中の確認には非同期Handlerを使い、描画同期の待ちに巻き込まれにくくする。メインスレッドを別の処理が占有している時間やAndroid側のAPI応答を省略するものではない。

起動条件・解除待ち・Activityへの受け渡し・1.18の待機／復旧処理は維持する。保存情報を先に読むため、その時間は履歴表示前へ移る。起動から終了までの総時間を必ず短縮する変更とは扱わない。アイコン側は既存の方式を維持する。

1.19時点では、ボタンがまだ使えなければ従来の確認間隔・5秒以内の期限・クリック拒否時の再試行を使っていた。1.21では自動実行のUI操作後の期限と反映確認を上記のとおり変更した。ロック・消灯・設定OFFの確認、クリック対象の検証、起動ごとの重複防止は省略しない。履歴表示後にホームへ強制的に戻す処理や、画面を隠す処理は追加しない。

Androidやランチャーの応答・アニメーションは残るため、実機で「0ms」「見えない」ことは保証できない。今回の検証は実際のJavaコードを使った模擬環境で行う。区間ごとの値は診断で確認できる。

## 1.18.0の修正（維持）

自動起動が来ないという報告を受け、画面を消す速度ではなく、再起動後の待機・再開条件を見直した。

- 解除通知の受信設定を修正。Android 13以降でSystemUIなど別UIDのシステムアプリが送る通知も受け取る。対象はOS保護された4種類の通知だけに限定し、通知後も実際の解除・点灯状態を確認する。
- 15秒で確認を打ち切る方式を廃止。まだ未実行なら、短い確認期間の後も1秒間隔の軽い準備確認を継続する。通知が来なくても状態が整えば再開する。画面取得を伴う準備には時間制限と再開前の間隔を設ける。
- 消灯通知を受けた直後は操作せず、その後は実際の画面状態を確認する。点灯通知の取りこぼしだけで永久に待つ状態をなくす。
- ユーザー補助のフィードバック割り込みをサービス終了と取り違えない。終了時の後片付けはonDestroyで行う。
- 実行権を保存した後でも、実際のUI要求が一度も呼ばれていないことを生存中の処理で確認できる場合は、その処理自身の記録を戻して再開できるようにする。すでにUI要求を試みた場合や、プロセス終了で実行の有無を確定できない場合は繰り返さない。

これらはコードとAndroid標準の受信仕様から見つけた不具合。今回の端末でどの条件が発生したかは、新しい実機診断がないため未確定。

## 更新と使い方

同じパッケージ・署名で上書き更新できる。ユーザー補助と「再起動のたびに1回実行」のON設定は引き継ぐ。更新後は設定ONのまま端末を再起動し、ロックを解除する。

初回だけ、アプリの案内からユーザー補助の「履歴クリア」をONにする。設定と診断はアイコン長押しから開く。ホームアイコンは押すだけで消去を開始する。

「再起動のたびに1回実行」は初期状態OFF。ONにした時点の起動は基準として記録し、次の再起動から実行する。実行後もONを維持する。同じ起動内の重複通知・サービス再接続・遅延Activityで消去を繰り返さない。自動実行前のアイコン操作はその起動の試行として扱う。

Androidがユーザー補助サービスを接続し、初回ロック解除・画面点灯・キーガード解除が揃ってから動く。未接続・無効化・強制停止中は実行できない。再起動通知のreceiverからサービスやActivityを勝手に新規起動しない。追加権限はRECEIVE_BOOT_COMPLETEDのみ。定期アラーム・WakeLockは使わず、処理済み/OFF/サービス終了で待機を解除する。

## 消去の範囲と制約

Android 10以降。Samsung、AOSP Launcher3、Pixel Launcher、SystemUIの既知の画面と正しい「すべて閉じる」ボタンを検証する。SystemUIの通知削除ボタンを誤操作しないよう、独立した履歴画面の手がかりを要求する。画面画像やアプリ一覧は保存しない。

常駐アプリの強制終了はしない。クイック設定タイル、黒い覆い、スクリーンショット、端末全体のアニメーション設定変更は含まない。履歴画面自体は開くため、不可視や一定の実行速度は保証しない。

保存した実行権とAndroidのUI操作を一つのトランザクションにはできない。UI操作を試みた後に失敗・ロック・消灯・プロセス終了が起きても同じ起動で自動処理全体をやり直さない。明示的に拒否されたクリックは、同じ処理の期限内で新しい画面を検証して再試行する。自動実行では受付後も反映を確認し、同一画面の同一対象が残ることを再検証できた場合だけ上限付きで再試行する。これは「起動ごとの最大1回の自動試行」であり、OSによる実際の履歴削除成功を保証するものではない。

## 検証

実際のJavaコードを模擬Android環境で実行し、旧1.17との同条件比較、通知送信元の区別、遅い初回解除、通知の欠落、準備中の割り込み、複数回の再起動、二重実行防止を確認する。272項目のサービス・Activity模擬テストと57項目の照合テストが成功。現行のテスト結果はdist/host-test-results.json、1.20との起動直後の動作比較はdist/cold-boot-v1.20-v1.21.jsonに記録。1.19との学習済み経路の比較はdist/warm-inline-v1.19-v1.20.jsonを参照。旧1.18との区間比較はdist/fast-transition-v1.18-v1.19.jsonを参照。1.18時点の起動復旧比較はdist/boot-liveness-v1.17-v1.18.jsonを参照。

接続された実機・エミュレーターはなく、Samsung実機の再起動や画面表示時間は未検証。模擬テストはAndroidの実際のプロセス管理・Binder通信・端末描画・設定保存の耐障害性を検証しない。

## ビルド

Java 17と固定したAndroid SDK 35・ECJを使用する。必要ならpython3 setup_toolchain.py、続いてpython3 build.py、python3 validate_apk.py。サービスの検証はpython3 tests/service/run.py。

signingディレクトリとソース保存用ZIPは更新署名を含む非公開データ。公開対象はAPK、README.md、SHA256SUMS.txt、release.jsonのみ。
