# ULike v1.9.81 — 撮影から保存までの経路最適化

公開済み ULike v1.9.80 / Hiro Morphe Patches v1.0.213 を基準に、承認済みの案 S1〜S7 と R1〜R5 を実装します。新規配布は ULike v1.9.81 / 総合版 v1.0.214 です。R6 の段階別再開は含めません。

基準の配布物は不変コミット `28f2bcc5bee767041034935185be19b987d253d2` から取得し、単体版 SHA-256 `2be00d742db6a8954a08e0dc43c27b11e1fb2d20c864d09a77b8010bb9a1ea25`、総合版 SHA-256 `7fae185dcd460f194696cd12752535e49ac767092e60549bdee986b65c9e8022` に固定します。

## 保存・メモリ・初回準備

S1 は保存先の登録とファイル記述子の取得を先行し、HEIF エンコーダの生成だけを専用の利用権で待機させます。前のエンコーダが実際に閉じた通知で、次の写真の準備を一度だけ再開します。キャンセル時は準備処理の終了を待ち、未公開の保存先を回収します。

S2 は Java ヒープとシステムメモリを別々に確認し、実際の画像サイズ・処理段階・所有画像から必要量を計算します。確実に生存しているネイティブ画像の容量は、システムの空きメモリと重複して差し引きません。不明な情報、メモリ不足、異常な値には従来の保守的な制限を残します。保存キュー上限は 3、SDK の撮影処理は直列のままです。通常入力 4080×3060 と固定 24.5MP 設定の 5712×4284 を区別します。

S4 は writer の close、非同期コールバックの終了、ハードウェア解放を確認した後、ファイルの検査前に不要になった最終画像を解放します。元画像と検証中の画像は所有権に従って保持し、実際に解放できた時だけメモリ予約を減らします。

S7 はプレビューの描画確認後にコンストラクタのメタデータをキャッシュし、準備用ワーカーを起動します。ダミーの撮影や美肌処理、可変な SDK オブジェクトの事前生成は行いません。

## CPU と GPU の処理経路

S3 は GPU の演算時間だけでなく、利用枠の待ち、準備、転送、読み戻しと後段を含む完了時間で経路を選びます。通常の Strong 経路は、既存の画質証明と CPU に対する 5% 以上の速度条件が揃った場合に使用します。利用枠の待ちには 50ms の上限を設け、残りの完了時間予算がそれより短ければ先に CPU へ戻ります。同じ写真で観測した遅延も判断へ反映します。画像を GPU に保持して後段へ渡す経路でも、CPU に勝てる残り時間を待機期限に用います。

S5 は同じ写真・同じモデルの予備 NR でセッションとモデル転送を再利用し、残差処理用のバッファ容量も再利用します。所有者が使用中なら他のワーカーは待たずに CPU へ戻ります。この再利用は初回から独立した全出力一致と速度条件で認定し、従来の GPU 経路が CPU より遅いという理由だけでは候補から除外しません。従来の不一致記録は実行前と出力の確定前にも尊重します。

S6 は初回 Strong の重い画質比較を待機時間へ移し、撮影中に作る検証用コピーを制限します。GPU の全画像検証コピーは写真ごとに 1 件、新しい NR 再利用候補と Strong の認定が共有するストリップコピーは通常合計 32 MiB までです。最初の完全なストリップを分割せずに検証するための例外も、全体の 96 MiB 制限内で管理します。検証キューは処理の種類ごとに順番を回し、再撮影による中断が続いても、新しい写真から検証を進められるようにします。

R1 は予備 NR の CPU 退避を、呼び出し元の作業領域を使える経路へ統一します。バックグラウンドの比較処理は独立した作業領域を所有します。CPU が速くなった影響を再評価する速度記録は、元の GPU 画質認定・画質不一致記録と分離します。

R2 は GPU に画像を保持して Strong から後段へ渡す前に、変形・仕上げ・保護係数の容量を確認します。同時に生存する領域の最大値で予約し、実行時の再確認と失敗時の CPU 退避を保持します。R3 は保護マスクを作る前に経路を固定し、その経路に必要なマスクだけを一度生成します。量子化済みの値から元のマスクを近似復元する変更はありません。

R4 は変形のない CPU のモアレ処理とシャープ処理を、境界を含む帯ごとに連続処理します。中間の整数 ARGB 丸めと隣接画素の参照を維持します。対象は所有する書き換え可能な不透明 sRGB ARGB8888 画像で、独立した 2 回の全画素一致と、追加の不透明確認を含む 5% 以上の速度条件を満たした場合だけ利用します。他の画像形式・色空間・変形経路は従来処理を使います。

R5 は補正待ちの同じ写真を読み取り専用で解析し、顔と処理前のノイズ推定を再利用します。所有画像、設定、回転、撮影メタデータが一致する場合に限ります。縮小後・フィルタ後の推定は省略しません。正常な顔ゼロと解析失敗を区別し、失敗時は従来の解析を実行します。

## 画質と既存動作

解像度、NR・美肌・シャープの強度、肌・輪郭・暗部の保護、色空間、ビット深度、HDR / gainmap の扱い、保存形式と HEIF 設定を保持します。高速経路の条件に合わない入力には従来の処理を残します。単写の条件と、フュージョンを無効にする既存の DEX は同一です。

全 12 native ペイロード、GPU program 0〜50、native インストーラー、JNI は .80 配布物とバイト単位で同一です。CPU / GPU の既存の演算本体、整数中間結果、全画素比較を検査し、保存済みの GPU 認定と不一致記録の環境識別子を維持します。

`src/production1981.json` が再コンパイルする Java クラスを固定します。`SaveRuntimeHooks1981.java` による保存境界と顔解析成功通知の変更は、追加箇所・レジスタを検査したうえで、変更を逆変換すると元のクラスに完全に戻ることを証明します。その他の DEX、元アプリへ差し替えるメソッド、総合版の他アプリ資源とログの計算方法を保持します。
