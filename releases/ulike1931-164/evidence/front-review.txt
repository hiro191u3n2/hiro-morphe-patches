Concrete defects established by source + emitted baseline DEX inspection
1. VECameraCapture.onCaptureStarted calls PreviewStart1927.start(), ignores its
   return value, and still sends cameraOpenSuccess(). If the native preview input
   list has not arrived, startPreview returns -100. The later addCapturePipelines
   setter only signals an existing pending start.
2. PreviewStart1927.remember and its pending worker explicitly require route.rear.
   Thus a front-camera -100/-105/-1 readiness failure is not armed for retry;
   adding the missing front input later leaves the camera unstarted.
3. PreviewInputs1929.before renews released preview textures only for a current
   rear route. Original TECapturePipeline.isValid() checks positive dimensions
   and a listener, and TETextureCapturePipeline simply delegates to it. Neither
   validates SurfaceTexture lifetime. A released front SurfaceTexture therefore
   passes that test and can reach the native provider with an invalid target.
4. Original VECameraCapture.newSurfaceTexture() only sets its existing u flag.
   The subsequent original startPreview constructs the native TESurfaceTexture
   and notifies the existing capture listener. The repair uses this path.

The defects above explain executable ways to retain camera UI while no preview
image starts. They are consistent with the reported restart symptom, but an
actual Galaxy reproduction/logcat was not available to establish which defect
fired on this particular device.

Native lifecycle evidence and rejected extra change
- i.s.a.w.q.INSTANCE is the common Camera1/Camera2 server. Client ownership is
  mCameraClient == capture.o; getCameraState() alone is global and does not check
  the caller. Native states are closed 0, opening 1, opened 2, preview 3, closing 4.
- Camera1 hardware identity is i.s.a.w.d.H; Camera2 identity is i.s.a.w.g.K.
- stopPreview(boolean) does not clear capture.p; settings-based switch can retain
  the same Java capture/client while replacing hardware. Explicit cancellation
  and hardware-generation checks are consequently required.
- A proposed same-manager/provider reuse versus delayed release collision was
  investigated and excluded from this release. Whole-APK reference inspection
  finds exactly one q$k constructor site, q.destroy(). destroy first invalidates
  mIsInitialized, client and cached provider settings. Its later reconnect calls
  synchronized init(), which allocates a NEW provider manager. init/destroy use
  the same server monitor. The only write to mProviderManager is that init site.
  No ordinary native path establishing same-manager adoption after this release
  task was found. ProviderLease1931 was therefore not created.
