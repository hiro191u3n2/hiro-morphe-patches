# ULike v1.9.86 — 撮影間のGPU予測と仕上げ認定の修正

公開済みULike v1.9.85／Hiro Morphe Patches v1.0.218を固定基準として、撮影をまたぐ実測履歴、旧GPU基準が使えない仕上げ認定、診断表示を修正します。新規配布はULike v1.9.86／総合版v1.0.219です。

## 修正範囲

1. 遅いGPUの再評価までの1.5秒の待機状態と、撮影をまたぐ実測履歴を分離します。待機が終わっても履歴を消さず、12秒の有効期間・最大3撮影・64キーを維持します。別々の2撮影以上の実測がある場合だけ履歴を使い、認定値・有効履歴・同じ写真内のstage/bank実測の最大値から保守的に予測します。遅い履歴が有効な間はCPUを選び、履歴が不足した後は認定済み経路を再評価できます。
2. 旧GPUの仕上げ経路で有効な比較基準を作れない場合、新しい仕上げ候補を実際のCPU出力と実測時間で認定できます。独立した2回の全画素一致と、CPU最速に対してGPU最遅が5%以上速いことを要求します。有効な旧GPU基準がある場合は、CPUと旧GPUの両方に対する従来の速度条件を維持します。CPU基準が2試行で変化した場合は認定せず、真の画質拒否と実行不能・メモリ不足・取消を区別します。
3. 旧GPUと新GPUの各仕上げ候補について、一致回数・速度計測回数・比較基準・実測時間・不成立理由を記録します。Strongの時間予測は、有効撮影数・最古の有効観測の年齢・認定値・観測最大値・実際に使用した最終予測値を表示します。診断は小さな数値だけを保持し、保存済み写真の時間・GPU件数、採否・取消に影響しません。

## 保持と検証

画素の計算・NR・美肌・シャープ・保護処理・解像度・保存形式・カメラ/プレビュー/保存フックを保持します。全12 nativeペイロード、GPU program 0〜50、JNI、画質認定のキーと不一致記録は公開.85と同一です。独立した2回の全出力一致と実速度条件、GPU枠の待機上限、実際の転送予算、検証保持96MiBとコピー所有権を維持します。新しいnativeバイナリは作りません。

production1986.jsonで本体5ルートを限定し、diagnostic_methods1986.jsonでレビュー済みのメソッドと本体ソースを固定します。公開.85の全2121ソースはtests1986/source-scope85.jsonに固定し、旧版の試験を残して新版の正負の回帰を追加します。旧版と意図的に変わる履歴期限や仕上げ基準の期待値は、明示的な.86 wrapper内でのみ扱います。qa_contract1986.jsonは実行したホスト検証と必須要件を対応させます。

固定JDK21.0.8+9、Morphe1.16.0、Android/D8、NDKr27cを使用します。declare1986.py → build1986.py → validate1986.py → finalize1986.py → publication/publish1986.pyで再構築・公開します。原本APKSへの適用と完成APKの静的検査を行い、そのMPPとCIの再構築MPPを完全一致させます。原本適用の実行場所と実機未検証を明記し、過去の検証件数は今回実行した件数へ加算しません。
