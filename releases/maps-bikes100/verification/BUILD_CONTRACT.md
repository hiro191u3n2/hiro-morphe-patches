# Additive bicycle-marker build and verification contract

`src/build.py` builds `Maps_Hide_Bicycle_Marks_v1.0.0.mpp` and
`Hiro_Morphe_Patches_v1.0.369.mpp` from immutable bundle 1.0.368. The baseline
SHA-256 is
`b14644953b807eae4ed8b026aa6445b3806e9acab766e0d623f47e72af66de27`.

The integrated bundle preserves every baseline entry byte-for-byte except the
manifest and combined loader DEX. `BundleAudit` merges only the new
`app/hiro/mapsbikes/patches/` provider classes and checks canonical equality of
every baseline DEX class after writing the merged DEX. Existing compiled Java
provider classes, runtime extensions, contracts, and all other payloads remain
byte-identical. Both pinned Morphe SDK versions must list the same existing
provider names, descriptions, enabled state, compatible packages, and versions,
with exactly one new bicycle option.

## Source interface

- Provider: `src/patch/MapsHideBicycleMarksPatch.java`, package
  `app.hiro.mapsbikes.patches`, named `地図上の自転車マークを非表示`.
- Runtime: `src/runtime/BicycleMarkerFilter.java`, package
  `app.hiro.mapsbikes`, packaged as `extensions/maps_hide_bicycle_marks.mpe`.
- Runtime behavior test main: `app.hiro.mapsbikes.BicycleMarkerFilterTest`, with
  host fixture classes under `src/test-host/`.
- Actual APK/native contract audit: `src/test/MapsBikesAudit.java`.
- Additive loader merge audit: `src/test/BundleAudit.java`.

The patch and audit are compiled against `morphe.jar`; compiled providers also
run on `morphe-2.2.jar`, whose compatibility bridge supports the prior constructor
signature. The build checks real input APK guards under both SDKs.

## Actual APK verification

The build pins both previously supplied APKs by SHA-256. It creates these five
audited outputs:

| Label | Operation |
| --- | --- |
| `standalone-v285` | Apply the new standalone patch to the supplied v2.8.5 APK. |
| `integrated-v285` | Apply the same option from bundle 369 to the supplied v2.8.5 APK. |
| `reported-v287` | Apply the option from bundle 369 to the reported v2.8.7 APK. |
| `additive-to-existing-four` | Add the new option to the baseline 368 output with the existing four Maps options. |
| `all-five-maps` | Apply all five Maps options from bundle 369 to the supplied v2.8.5 APK. |

The reference APK is regenerated by applying the existing four Maps options
from immutable bundle 368. Its successful patch/rebuild result and exact input,
bundle, and output hashes are recorded separately as `baseline_application`.
An optional `--reference-dir` reuses a cache generated by that exact operation.
The build verifies its source APK hash, bundle hash, output APK hash, report
hash, exact selected patch names, successful patch/rebuild steps, and provenance
schema, then runs both native guard SDKs against the cached APK again. The cache
must contain `patched.apk`, `morphe.json`, and `provenance.json`; an incomplete
or changed cache is rejected.
The fifth output is audited against this reference, so preserving existing
startup, category-row, back-exit, and strict-search implementations is checked
on actual APK class data.

`MapsBikesAudit guards` verifies the native contracts, package/version/code
rejections, missing owner, unknown method body, and repeated application. Failed
applications must leave the mutable input unchanged. `audit` checks exactly
five added instructions at the beginning of the verified `Lbkbv.b` factory,
35 unchanged registers, the non-matching branch back to the original entry,
and the null return only when the runtime filter requests hiding. Canonical
equality with the expected minimal edit checks all original method bodies,
exception regions, fields, and metadata. Every unrelated class and every
non-DEX, non-signature ZIP entry is retained. Injected runtime classes must match
the compiled extension exactly, without class collisions or extra classes.

The two fresh-input standalone/integrated APKs must have identical ZIP entry
names and bytes. The additive/all-five pair must have identical class
implementations/metadata and non-DEX resources, checked by `compare`.
`all_five_additive_apk_contents_equal` records this class/resource equivalence;
`all_five_additive_zip_entries_identical` separately records whether the ZIP
entry bytes also match, including DEX placement and binary layout.

## Renderer scope

The native hook is the **SharedLabeler placed-label factory**. The APK contains
alternate rendering backend branches, and the available evidence does not
establish that every GeoXP or standard 2D rendering route calls this factory.
The QA record therefore has `all_rendering_backends_verified: false`.
Alternate backends and unrecognized future icon forms may retain bicycle
markers. Successful factory, host, and APK checks do not establish complete
visual suppression across every backend.

## Build invocation

Run `src/build.py --help` for the paths. Required inputs are `--base`, `--tools`,
`--work`, `--dist`, `--apk`, `--reported-apk`, `--java-home`, and `--timestamp`.
The work directory must not exist, and the distribution directory must be
absent or empty. `--java-home` points at the directory containing the validated
`bin/java` and `bin/javac` wrappers. The timestamp is a JST local release time in
`YYYY-MM-DDTHH:MM:SS` format. All artifact filenames and hashes are emitted in
the QA JSON only after the entire validation sequence passes.

Host behavior, native contracts, real APK patching, loader preservation, and
resource/class preservation are executable gates. This environment has not run
the modified app in an Android emulator or on a physical Android device, and
the QA record explicitly keeps those flags false. Actual Android UI behavior
is not claimed by these checks.
